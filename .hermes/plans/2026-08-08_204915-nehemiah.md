# Nehemiah Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Turn Nehemiah from a single-host Firecracker service into **Nehemiah** — a secure, multi-tenant managed cloud running initially on Latitude bare metal.

**Architecture:** Keep `nehemiahd` as the per-host data-plane daemon. Add a central TypeScript control plane for tenants, API keys, machine placement, usage, and provider orchestration; add a public gateway for REST/WebSocket/preview routing; connect hosts over a private network. PostgreSQL is the source of truth, S3-compatible object storage holds durable artifacts/templates, Cloudflare fronts the public edge, and Latitude is accessed through a provider-neutral capacity adapter.

**Tech Stack:** Go/Firecracker (`nehemiahd`, gateway), TypeScript/Effect (`apps/nehemiah`), PostgreSQL/Neon, S3-compatible storage, Cloudflare, Stripe, Latitude API, SvelteKit dashboard, Vitest/Playwright, Go tests.

---

## Product boundary and launch target

The first sellable product is not “every feature from E2B, Orgo, and Daytona.” It is:

> Forkable computers for AI agents: shell, browser, desktop, code execution, snapshots, and live previews from one isolated microVM API.

### Private-beta acceptance criteria

- One production region on at least three Latitude hosts.
- Organizations can create scoped API keys and launch, inspect, exec, connect to, extend, fork, and destroy machines.
- Browser desktop, TTY, file transfer, and preview URLs route through the Nehemiah endpoint without exposing hosts.
- Machines are tenant-scoped; cross-tenant access tests pass.
- Hosts register, heartbeat, drain, and stop receiving placements when unhealthy.
- Capacity and quota failures are deterministic and do not overcommit hosts.
- Every billable lifecycle event is durably recorded once.
- Jailer, cgroups, network isolation, metadata blocking, TTL cleanup, and host-level limits are enabled.
- Central logs, metrics, traces, alerts, and audit logs exist.
- A host-loss drill marks affected machines lost and routes new capacity elsewhere.
- SDK, CLI/MCP, dashboard, quickstart, status page, and support runbook are available.

### Explicit non-goals for private beta

- Multi-region scheduling.
- Live migration of running microVMs.
- GPU machines.
- Marketplace-style public templates.
- Enterprise SSO or custom contracts.
- Automatic scale-to-zero bare-metal provisioning.

### Trust boundaries

- Only the gateway/control plane is public.
- `nehemiahd` accepts only authenticated internal traffic over the private host network.
- Customers never receive host addresses or host tokens.
- Public machine IDs map to host-local IDs in PostgreSQL.
- User API keys are hashed at rest and scoped to an organization/project.
- Provider and Stripe credentials exist only in control-plane secrets.
- Guest traffic cannot reach host services, RFC1918 networks, cloud metadata endpoints, or other guests.

## Lessons adopted from the smol-machines ecosystem

The review covered all nine organization repositories: `smolvm`, `smol`, `smolvm-sdk`, `smolbench`, `harbor-smolvm`, `dagger-smolvm`, `homebrew-tap`, and the `libkrun`/`libkrunfw` forks. Keep Firecracker as Nehemiah's VMM; adopt the product and reliability patterns rather than replacing the engine.

### Mandatory plan additions

1. **Guest agent over vsock:** replace serial-console command execution and file transfer with a small B.C guest agent supporting readiness, exec, streaming stdout/stderr, PTY, file transfer, cancellation, and liveness. Keep serial as recovery/debug transport. Add this to Phase 1 before Nehemiah API work.
2. **Started is not ready:** model `started_at`, `ready`, and `ready_at` separately. A machine is customer-usable only after the guest agent responds and requested ports pass readiness checks.
3. **OCI-native images:** allow an OCI image reference as a machine source, cache layers per host, verify digests, and expose pull progress. Templates remain the fast/forkable path; OCI makes the platform broadly usable.
4. **One local/Nehemiah SDK contract:** expose the same `Machine` API against local `nehemiahd`, self-hosted endpoints, and Nehemiah. Unsupported target-specific features must return typed `NotSupported` errors rather than silently behaving differently.
5. **OpenAPI as wire-contract source:** generate the Nehemiah OpenAPI document from server types and use it to validate/generate Node, Python, and Go SDK models. Hand-written ergonomic wrappers may sit above generated wire types.
6. **Strict egress policy:** network off by default; add CIDR and hostname allowlists with DNS interception, TTL-clamped learned IPs, DNS-rebinding protection, and a non-overridable Nehemiah hard floor blocking metadata, loopback, link-local, RFC1918, unique-local, CGNAT, host, control-plane, and peer-tenant ranges.
7. **Lossless daemon restarts:** launch each Firecracker process in a sibling systemd scope, detach it from `nehemiahd` shutdown, persist its lease/agent socket metadata, and reconnect after daemon restart. Draining must be an explicit fleet operation, not an automatic service-restart side effect.
8. **Elastic memory:** evaluate Firecracker's balloon device/free-page reporting so scheduler reservation can distinguish configured memory from observed resident usage. Do not overcommit memory until stress tests prove a safe policy.
9. **Golden machine fork pools:** make batch fork a first-class API with all-or-cleanup semantics, readiness checks, and optional retained golden templates for agent evaluations and parallel coding tasks.
10. **Benchmark gates:** create a B.C equivalent of `smolbench` covering cold start, restore, first exec, fork/fork-batch, CPU, disk, DNS, HTTP, TTY/VNC latency, and gateway overhead. Store JSON results with min/max/median/standard deviation and fail releases on material regressions.
11. **Ecosystem adapters:** after the core API stabilizes, build Harbor and Dagger integrations. Harbor provides a concrete agent-evaluation workload; Dagger makes B.C useful for hardware-isolated CI.
12. **Distribution quality:** add signed/checksummed CLI releases, Homebrew packaging, provenance attestations, and automated release workflows. Checksums must fail closed if verification metadata is unavailable.
13. **Device-flow CLI login:** support browser/device authorization plus silent refresh for humans, while retaining scoped `bc_...` API keys for automation. Never log authorization headers or persist tokens in project files.
14. **Portable environment declarations:** define a small `Nehemiahfile` format for image, resources, network policy, ports, setup commands, persistence, and forkability. Keep it declarative and provider-neutral.

### New pre-beta performance targets

Record baselines first, then choose numeric SLOs from measured Latitude hardware rather than marketing guesses. At minimum track:

- cold boot and snapshot restore to guest-agent ready
- first exec round-trip
- single and batch fork to ready
- TTY and VNC connection setup
- preview gateway overhead
- sequential/random disk performance
- DNS/HTTP egress latency
- memory RSS versus configured guest memory
- machine cleanup and orphan rate

## Major risks and mitigations

1. **Guest escape or lateral movement** — mandatory jailer/seccomp/cgroups, private-network blocks, image signing, external audit.
2. **Bare-metal capacity lag** — static beta fleet, utilization alerts, manual Latitude provisioning first, provider-neutral adapter later.
3. **Host loss destroys machine state** — clearly define ephemeral semantics; durable files live in volumes; mark machines lost honestly; no false HA claims.
4. **Preview/WS gateway becomes bottleneck** — isolate gateway from control API, load-test long-lived sockets, add horizontal replicas and connection draining.
5. **Billing disputes** — append-only idempotent usage events, shadow metering, customer-visible usage, no charging before reconciliation is proven.
6. **Ruth/Ezekiel distract from core Nehemiah work** — use them as dogfood; do not pull unrelated personal-agent capabilities into Nehemiah.
7. **Competing with three products at once** — lead with forkable shell+desktop machines; add broader workspace features only after the core is reliable.

## Open decisions to resolve before Phase 2

- Control-plane deployment target and long-running job mechanism.
- WireGuard orchestration versus another private host-network solution.
- PostgreSQL provider and object-storage provider for production.
- Cloudflare gateway topology and wildcard preview-domain strategy.
- Initial machine sizes and pricing units.
- Ephemeral-only versus persistent machines in private beta.
- Whether inference/computer-use model charges are pass-through or customer-supplied keys.
- Data retention, deletion, and regional residency policy.

Recommended defaults: Neon PostgreSQL, S3/R2-compatible storage, Clerk for dashboard identity, B.C API keys for SDK access, Stripe for billing, WireGuard private host network, Cloudflare edge, static Latitude fleet for beta.

## Recommended execution order

Do not start with billing or the dashboard. Execute in this order:

1. Threat model and architecture decisions.
2. `nehemiahd` hardening, host identity, restart reconciliation.
3. Control-plane database, tenants, and API keys.
4. Heartbeats and transactional scheduler.
5. Nehemiah machine API and public gateway.
6. Multi-host lifecycle and failure reconciliation.
7. Durable templates/volumes.
8. Shadow metering and quotas.
9. Dashboard, SDK, CLI, and MCP.
10. Dogfood, security review, private beta, then billing/public beta.
